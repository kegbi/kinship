# Audit Remediation Plan — 2026-11-07

Status: proposed and user-directed (2026-11-07). The source is the
[architecture, security, and performance audit](../validation/audit-2026-11-07/README.md)
of commit `bc8579ae` and its five area reports. This plan is subordinate to
`AGENTS.md` and to the accepted schema, architecture, and product contracts. The
product owner approved decisions D1–D4 on 2026-11-07 (Part 3, ADR 0007, and ADR
0008), so no ticket waits for a decision.

The plan closes all 70 finding IDs: FEQ-01–13, BEQ-01–15, SECA-01–15,
SECT-01–11, and FER-01–16. Four pairs share one root cause, and the same ticket
closes both members of each pair: FEQ-01/FER-04, FEQ-07/FER-07, FEQ-12/FER-08,
and FEQ-13/FER-11. Part 6 maps every ID to its ticket. Ticket AUD-P2 records
each ID's closure in the audit README.

A finding is **closed** in one of three ways:

- **Fixed:** the ticket is integrated and its regression test proves the fix.
- **Decided:** a recorded decision rejects or defers the change, and names what
  would reopen it.
- **Documented:** the finding is informational, and its action is a recorded
  note or constraint.

## Part 1 — Ground rules

### 1.1 What is already right (do not "fix" these)

The audit verified the following. Every ticket must preserve them, and a
reviewer treats a regression of any of them as a blocker.

- **Route protection.** All 142 protected routes refuse anonymous, empty,
  malformed, unknown, and revoked cookies. All 84 cookie-authenticated unsafe
  routes reject a foreign, missing, or `null` `Origin`.
- **Sessions.**
  - Tokens are 256-bit, and only a SHA-256 digest is stored.
  - The cookie is `HttpOnly; Secure; SameSite=Strict`, with a 12-hour absolute
    lifetime and a new token on every sign-in.
  - Sign-out, password reset, suspension, and identity deletion all invalidate
    sessions on the server.
  - A password-only MFA session reaches only the challenge.
- **Tenant scoping.** No cross-workspace path exists. Workspace B sent 964
  attack requests carrying A's ids, and all 657 rows that reference A's ids were
  unchanged. An `X-Workspace-Id` for a foreign workspace answers 401. Invitation
  tokens are bound to the invited address.
- **API tokens.** Tokens are 256-bit, hashed, compared in constant time, and
  carry independent scopes. A refused `Authorization` header never falls back to
  the cookie. Demotion takes effect at use time, and suspension kills the token.
- **Calendar feeds.** The secret is 256-bit, sits in the path, is stored hashed,
  and can be revoked. The gateway rate-limits each feed.
- **Database access.** Queries are set-based, keyset-paginated, and bounded.
  Per-person paths use indexes. The worker claims rows with
  `FOR UPDATE SKIP LOCKED` correctly.
- **Frontend.**
  - All 39 delivered pages are served with their cataloged strategy.
  - Public and auth pages ship no React.
  - There is no client router.
  - Person-page zones load lazily below the fold, and `POST /view` waits for
    idle.
  - The notification poll runs once a minute per visible tab.

### 1.2 Verified facts that shape the fixes

1. **SECT-03 needs an application fix, not a schema fix.** The orchestrator
   tested this in a throwaway PostgreSQL 18.4 container with two cascade paths.
   - `ON DELETE RESTRICT` fails the workspace delete.
   - Plain `NO ACTION` fails it the same way, because PostgreSQL checks it at
     the end of the cascaded internal statement.
   - `NO ACTION DEFERRABLE INITIALLY DEFERRED` succeeds, but it moves the "type
     in use" error from the DELETE to COMMIT.
   - Deleting `people` before the workspace succeeds with the existing keys.

   AUD-M1 therefore deletes in dependency order, and the schema keys stay.
2. **Durable MFA challenges need v13.** The v12 SQL limits
   `user_sessions.purpose` to `authenticated`, `verified-entry`, and `legacy`,
   so a durable MFA challenge row needs v13 (AUD-V1, then AUD-A4).
3. **Version-7 ids cannot come from a column default yet.** The schema matrix
   still runs PostgreSQL 17.10 (`deno task test:schema:matrix`), which has no
   `uuidv7()`. They must be generated by the application or by a function
   compatible with PostgreSQL 17.
4. **Why the preference reads serialize (FEQ-01).** Chromium serializes
   identical concurrent requests for a URL it might cache. Passing
   `cache: "no-store"` to `fetch` bypasses the HTTP cache and its lock, and
   single-flight removes the duplicate requests altogether.
5. **A schema bump touches about 38 files.** See `8b3d2c7b`: the SQL,
   specification, catalogs, mappings, migrations, validation JSON, generated
   Kysely types, the read lists in `deno.json`, `Dockerfile.api`,
   `compose.yaml`, `AGENTS.md`, the architecture docs, and the migration tooling
   and its tests.
6. **Compressing authenticated JSON is not the usual BREACH risk here.** The
   session cookie is `SameSite=Strict`, and bearer requests carry no cookie, so
   a cross-site page cannot trigger authenticated requests. That removes the
   usual BREACH precondition. Responses that return a secret are still excluded
   (D4).
7. **Some failures are already known.** The Parked Work section of
   `active-delivery.md` lists open REL items; for example, REL-095 through
   REL-104 block the API integration checkpoint. A matching failure is known. Do
   not fix it inside these tickets.

## Part 2 — Execution protocol

### 2.1 Per ticket

The per-ticket loop is the one in
[`autonomous-delivery.md`](../development/autonomous-delivery.md) and the
`run-tdd-ticket-loop` skill.

1. The implementer reads `AGENTS.md`, `autonomous-delivery.md`, Parts 1 and 2 of
   this plan, the ticket, and the audit sections the ticket cites. Do not
   re-audit; the evidence is recorded.
2. **RED:** the ticket's listed failing test, observed failing before any
   production change. **GREEN:** the smallest change that complies with the
   architecture. **REFACTOR:** clean up while focused tests stay green.
3. Hard constraints:
   - The schema stays at v12 except in V-lane tickets.
   - Every mutation goes through the facade of the module that owns the table.
   - Read models stay read-only.
   - `apps/web` never imports `packages/backend`.
   - No new framework or validator unless the ticket names it.
4. Verify:
   - the ticket's Verify list;
   - `deno task fmt:check` and `deno task lint`;
   - the affected `check:*` tasks;
   - `deno task contracts:generate` then `contracts:check`, whenever a contract
     changes;
   - `check:architecture`, whenever imports change.

   Do not run the all-browser matrix per ticket.
5. Produce one candidate commit and get one clean, read-only review. Then tick
   the checkbox here and add one evidence line:
   `Delivered <date>: <tests>, <coverage of changed scope>, <gates>.`

Sizes: S ≤ 1 day; M = 2–5 days; L = 1–3 weeks of focused implementer time.
Priorities: **urgent**, then **high**, **normal**, and **low**.

- **When a ticket may start.** A ticket starts once every ticket in its Depends
  line is integrated and its decision (if any) is answered.
- **Parallel implementers.** Several implementers run at once, each in its own
  isolated checkout taken from the head of the integration branch. Two tickets
  may run at the same time unless one depends on the other. Part 5 lists the
  files that unchained tickets share.
- **Integration is serialized.**
  1. Rebase the approved candidate onto the current integration branch.
  2. Rerun its Verify list.
  3. Fast-forward the integration branch.

  A rebase conflict goes back to the same implementer as an amendment, and the
  reviewer re-checks the rebased diff.
- **One schema version at a time.** Only one V ticket may be in flight. No other
  ticket edits `personal-crm-schema/`,
  `packages/backend/platform/postgres/generated/`, or `tools/migrations/`.
- **Later tickets must keep the guards green:**
  - After AUD-K5 lands, every ticket that adds a route keeps its default-deny
    sweep green.
  - After AUD-G3 lands, every ticket that changes UI keeps the CSP check green.
  - After AUD-P1 lands, every ticket keeps the budgets green.

Run each checkpoint once, on the integration branch:

- **C1**, after AUD-A1, AUD-M1, AUD-W1, and AUD-K1: root `check`, `test`,
  `test:coverage`, `contracts:check`, and `check:architecture`, plus the

A failure gets one bounded reproduction. If these tickets caused it, append a
corrective ticket `AUD-XN-fix` under that ticket and run it through the same
loop. Otherwise, append a REL item to Parked Work in `active-delivery.md`.

**D1 — B: render on demand only where the first response needs request-time
data.**
[ADR 0007](../architecture/decisions/0007-on-demand-rendering-only-for-request-time-content.md)
records the decision and amends ADR 0001. AUD-G5 implements it:

- `/privacy` and `/terms` render on demand from the API's public legal-document
  read. A gateway `proxy_cache` of about five minutes is in front, and the pages
  read without JavaScript.
- `/auth/verify-email`, `/auth/reset-password`, `/auth/mfa`, and
  `/app/compliance` are prerendered. `/invite/:token` gets an internal shell.
  nginx serves all five with `Cache-Control: private, no-store`.
- Astro uses `output: "static"`, so pages are prerendered unless they opt out.
- The renderer image carries only runtime dependencies, and the gateway's health
  no longer depends on the renderer.
- Rejected: A (retire the renderer), because `/privacy` and `/terms` would stay
  client-fetched; and C (status quo), because it renders identical HTML per
  request and couples the gateway's health to that.

**D2 — Approve: the database enforces workspace isolation.**
[ADR 0008](../architecture/decisions/0008-database-enforced-workspace-isolation.md)
records the decision, and AUD-V2 implements it in schema v14:

- the `kinship_migrator`, `kinship_app`, and `kinship_worker` roles, the last
  two with `NOBYPASSRLS`;
- `UNIQUE (workspace_id, id)` keys and composite tenant foreign keys;
- `FORCE ROW LEVEL SECURITY` with
  `workspace_id = nullif(current_setting('app.workspace_id', true), '')::uuid`,
  set by `SET LOCAL` inside each transaction.

ADR 0008 lists the constraints the implementation must keep: `nullif`, no
session-level `SET`, every tenant query inside such a transaction, and narrowly
scoped cross-workspace paths. Rejected: roles only, because the database still
accepts cross-workspace references; and defer, because isolation stays one layer
deep.

**D3 — Avatars only.** AUD-K7 implements it:

- An avatar's content is addressed by its file id, so a new image gets a new
  URL. `private, max-age=86400, immutable` lets the browser reuse it across
  pages without revalidating. `private` keeps it out of shared caches.
- JSON reads and document downloads stay `private, no-store`. They carry
  personal data that must not persist in a shared computer's disk cache. The
  client keeps `cache: "no-store"` (AUD-F1).
- FEQ-08's ETag item for JSON is therefore Decided, on privacy grounds.
- Rejected: ETags on JSON with `no-cache`, because the browser would then store
  personal data; and the status quo, because every page re-downloads unchanged
  avatars.

**D4 — Compress, except secrets.** AUD-G2 implements it:

- The gateway gzips `application/json` and `image/svg+xml`, and serves
  pre-compressed static assets.
- Excluded are the responses whose body carries a secret: API-token creation,
  calendar-feed creation and rotation, and export-download token issuance. As a
  conservative default, so are the credential endpoints: sign-in, MFA,
  registration, email verification, password reset, and invitation steps.
- AUD-G2 enumerates the exclusions from the route registry and tests them. The
  reasoning is Part 1.2 item 6.
- Rejected: the status quo, which ships JSON about 70% larger.

**D5 — Keep sent reminder occurrences (standing default).** BEQ-07 and BEQ-15
are Decided for retention. The partial indexes in AUD-V1 exclude the sent
history, so it costs storage only. AUD-P1 records a size ceiling for
`reminder_occurrences`, and crossing it reopens the decision.

**D6 — Accepted as designed (standing defaults).** The user may override any of
these:

- FER-16: in-app navigation is a full document load. ADR 0006 rules out a client
  router; AUD-F1–F3, F6, and the lazy shell islands of AUD-F2 shorten each
  click, and AUD-P1 records the navigation timings.
- SECT-10:
  - The workspace slug is globally unique. A 409 reveals only that a slug
    exists, and no public route uses slugs.
  - Object keys carry no workspace prefix, because the metadata lookup is the
    barrier. AUD-V2 may add the prefix (ADR 0008).
- SECA-13 item 3: HSTS stays without `includeSubDomains` and `preload` for an
  owner-operated host. AUD-G1 documents this.
- SECA-14 items 1 and 2: TOTP enrolment stays in the backlog
  (`docs/planning/research.md:106`). Future enrolment must generate recovery
  codes of at least 128 bits.
- FER-12: the accepted `font-display: swap` without preload stays. AUD-F9 fixes
  the layout shift with a metric-matched fallback font.
- BEQ-10 (`last-contacted` ordering) and BEQ-11 (trigram index): no projection
  and no trigram index until AUD-P1 measures the query above its ceiling. AUD-Q4
  is conditional on that measurement.

## Part 4 — Tickets

### Lane A — Accounts and sign-in

- [x] **AUD-A1 — Registration cannot plant a password on someone else's
      address.** L. Urgent. Depends: none. Closes: SECA-01, SECA-02, and SECA-13
      item 6 (the Origin half).
  - Problem:
    - SECA-01: `POST /api/v1/registrations` stores the requester's
      `password_hash` on an active, unverified user
      (`identity/adapters/postgres/identity_repository.ts:19-26`). Verification
      only sets `email_verified_at` (`email_verification.ts:79-83`). So whoever
      registers an address first can sign in once its owner clicks the
      verification mail. Through a pending invitation, that person also joins
      the inviting workspace.
    - SECA-02: answering 409 for an existing address reveals that the account
      exists.
    - SECA-13 item 6: three public POSTs accept cross-site requests.
  - Scope:
    1. Bind verification to the browser that registered. Registration sets a
       random verifier in an `HttpOnly; Secure; SameSite=Strict` cookie and
       stores its hash with the verification token. A verification without the
       matching verifier still verifies the address, but discards the stored
       `password_hash` and sends the user to set a password, reusing the
       password-reset step. Verifying on another device therefore asks the owner
       to set a password once.
    2. A registration for an address whose only account is unverified replaces
       that pending account, voids its old tokens and handoffs, and answers 202.
    3. A registration for a verified address answers the same 202 and mails "you
       already have an account", with a reset link. The verification-retry path
       gets the same response equalizer.
    4. Mail the address whenever its password is set or changed.
    5. An invitee whose address has only an unverified pending account can
       register through the invitation, replacing that account, instead of
       getting `409 invitation_registration_unavailable`.
    6. Add the Origin check to `registrations`, `email-verifications`, and
       `email-verification-deliveries`.
    7. UI and contracts: update sign-up (no "already registered" branch),
       verify-email (the set-password branch), and the generated client.
  - Non-goals: provisioning at verification (AUD-A2); quotas (AUD-M3); MFA
    enrolment.
  - RED: an integration test beside
    `tests/integration/registration_postgres_test.ts` replays the 03 report's
    SECA-01 sequence: register X with password P, verify with the mailed token
    but without the registrant's verifier, then `POST /sessions` with P. It must
    answer 401; today it answers 200. A second test replays the invitation
    variant: the attacker's sign-in fails, and the invitee joins with their own
    password.
  - Verify: `deno task test:integration --module=identity` and
    `--module=workspaces`; `deno task test:unit --module=workspaces` and
    `--module=web`; contracts;
    `deno task test:e2e tests/e2e/registration.AUTH-001.spec.ts tests/e2e/invitations.AUTH-002.spec.ts --project=chromium`.
  - Delivered 2026-11-07: both SECA-01 takeover sequences now refuse the
    registrant's password (401) and the invitee joins with their own; SECA-02
    parity tests show a fresh, pending, verified, over-limit, imported, or
    disabled address answers alike with one provider call; Origin is refused on
    the three public POSTs; identity integration 6 passed (only the known
    REL-099), workspaces integration 6, workspaces unit 159, identity unit 12,
    web unit 1719 (only the 4 baseline failures); E2E AUTH-001 (including
    verification in another browser) and AUTH-002 8 passed on Chromium; changed
    backend scope 96.1% lines, 86.7% branches, 98.7% functions; contracts, fmt,
    architecture, and lint (only REL-096). The verifier is stored as a
    `registrant:`-prefixed `email_verification_tokens` row; AUD-M3 must cap the
    account-exists mail with the same per-address ceiling.

- [ ] **AUD-A2 — Registrations and authentication rows are bounded and purged.**
      M. High. Depends: AUD-A1, AUD-W2. Closes: SECA-04, and the session and
      request-log retention part of BEQ-15.
